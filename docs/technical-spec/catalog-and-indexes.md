# Catalog and indexes

## TS-17 Catalog and statistics

- **Decision**:
  - **Catalog tree.** One B+tree per database, with immutable stamped entries ([TS-14](transactions-and-recovery.md#ts-14-mvcc)). Catalog writes join the transaction's write set, so DDL and data changes commit and roll back together.
    - `(parent_id, name) → (object_id, kind, owner, definition)` for directories, schemas, graph types and graphs. `object_id` is monotonic and never reused. Its counter, and the token counter, are persisted like the element-identifier counter ([TS-07](storage.md#ts-07-element-identifiers)).
    - Reverse entries `object_id → (parent_id, name)` for paths and listing.
    - Token tables `(kind, name) ↔ token_id` for labels, edge types and property keys.
    - Index and constraint definitions keyed by `(graph_id, object_id)`, after the kind byte 5, 8 bytes big-endian each. Value: kind (2 bytes), entity, state, then token, tree, side tree, link and the type set of a property type constraint (0 otherwise), 8 bytes little-endian each, 44 bytes in all; then the property keys, 8 bytes little-endian each (`SchemaDef::encode`, `src/index/mod.rs:299-344`).
  - **Tokens.** Token entries carry no stamps and are never deleted ([TS-06](storage.md#ts-06-graph-layout)). Lookups use an in-memory map of the committed tokens, loaded at open.
    - A missing token is created at once, in an inner transaction: under a per-database token latch, the creator looks the name up again, draws a token identifier ([TS-07](storage.md#ts-07-element-identifiers)), commits the entry as a commit of its own ([TS-16](transactions-and-recovery.md#ts-16-commit-protocol)), adds it to the map and releases the latch.
    - The token stays whether the transaction that needed it commits or aborts. Two transactions that need the same name therefore get the same token, under snapshot isolation too.
    - **Token check.** Graph writes refuse, with `InvalidArgument`, a label identifier that is not a label token and an edge-type identifier that is not an edge-type token (`tokens_are`, `src/storage/graph.rs:251-267`; `Tokens::kind`, `src/catalog/mod.rs:452`). Property keys are not checked.
  - **Catalog names.** Creating or dropping a catalog object takes the X lock on its `(parent_id, name)` ([TS-15](transactions-and-recovery.md#ts-15-serializable-isolation-and-write-locks)). Of two transactions that create the same name, the second waits for the first; if the first commits, the write-write rule fails the second with 25N11, under snapshot isolation too.
    - **Parents.** Creating an object in a directory or schema takes the S lock on the parent's name (`src/catalog/mod.rs:1069-1079`). Dropping a directory or schema takes X there, fails with `NotEmpty` if its snapshot sees a child, then reads the latest committed children: a child created after its snapshot fails it with 25N11 unless the child's drop has committed. That read can see a drop that is later undone ([TS-16](transactions-and-recovery.md#ts-16-commit-protocol) step 6), so for each such child the dropper takes the S lock on the child's name, which waits for the child's dropper to end, and reads the child again (`none_created_later`, `src/catalog/mod.rs:1272-1323`; `drop_object`, `:1211-1247`). Under serializable isolation the drop still fails at validation when such a child exists, because the child's creation wrote into the children range of its read set (FR-TX-009; test `a_child_created_and_dropped_after_the_snapshot_fails_only_a_serializable_drop`, `src/catalog/tests.rs:724`). Without the parent lock or the children read, under snapshot isolation a schema could be dropped while a graph is created in it.
  - **Graph types in use.** Creating a graph takes the S lock on its graph type's name (`src/catalog/mod.rs:1173-1179`). Dropping a graph type fails with `GraphTypeInUse`, of GQLSTATUS class G1, "dependent object error" (`src/storage/error.rs:95-97`), while a graph its snapshot sees uses it, and with 25N11 if a graph using it was created after its snapshot and that graph's drop has not committed, by the read of Parents (`graph_type_unused`, `src/catalog/mod.rs:1249-1270`). The error does not yet return a GQLSTATUS code (`Error::gqlstatus`, `src/storage/error.rs:217-223`).
  - **Creation.** A new database's catalog contains a default schema named `public` and, in it, a default graph named `lpg`, so the default graph's catalog path is `/public/lpg` (user decision 2026-10-08, DECISION 191 on rmp task #31; `src/catalog/mod.rs:117-123`). `create` takes their owner principal as a required argument and records it as the owner of both (user decision 2026-10-07, rmp task #25; [interfaces.md](interfaces.md#public-api-shape)). Directories are created only through the Rust API.
    - **Durability.** `create` writes the catalog tree, with the two entries frozen (no stamps, [TS-06](storage.md#ts-06-graph-layout)), directly into `data-1` before its `sync_data`, and only then writes `CONTROL` ([TS-05](storage.md#ts-05-files-and-pages) Create). No WAL is involved: a crash before `CONTROL` exists leaves no database, and after it the objects are on disk. Every open therefore finds them.
    - **No authorisation.** `create` makes no authorisation request ([TS-23](interfaces.md#ts-23-authentication-and-authorisation)): no session exists, and the owner it receives is the first principal the catalog knows.
  - **Dropping a graph.** `DROP GRAPH` stamps the entry deleted and drops the graph's indexes and constraints in the same transaction (`drop_graph_schema`, `src/index/mod.rs:1408-1421`); garbage collection frees the graph's trees after the horizon passes.
  - **Closed graph types.** Graph types are immutable once created. Each `INSERT`, `SET` and `REMOVE` on a graph of a closed type is checked at the end of its statement against that type, over the elements the statement wrote. Open graph types cost nothing. The exact matching rules are in the General Rules, outside the ISO inserts: provisional (OQ-005).
  - **Statistics.** Node counts per label; edge counts per `(label, edge type, direction)` with the label on one side; entry and distinct-key counts per ONLINE index, where a distinct key is an index key without its element (`prefix_of`, `src/index/mod.rs:478-482`). An index's counts start with the counts its builder made, carried by the ONLINE commit ([TS-18](#ts-18-indexes-and-constraints) step 6).
    - Kept in memory and updated by the committer when it applies a commit ([TS-16](transactions-and-recovery.md#ts-16-commit-protocol) step 6).
    - **Below zero.** A count that a commit would take below zero is set to 0; the update never panics under the commit latch. The integrity check reports the drift by comparing the statistics with a recount ([TS-12](storage.md#ts-12-checksums-corruption-and-integrity-check); `Stats::apply`, `src/catalog/stats.rs:191-210`).
    - **Label changes.** When a commit adds or removes a label of node `n`, the committer changes that label's edge counts by every adjacency entry of `n` that the commit neither creates nor deletes, read from `n`'s adjacency prefix ([TS-06](storage.md#ts-06-graph-layout) Expansion). Edges that the commit creates or deletes are counted with `n`'s labels after or before the commit. This scan of the node's edges runs inside the serial section, because writers of edges at `n` hold only the S existence lock, which a label change does not block ([TS-15](transactions-and-recovery.md#ts-15-serializable-isolation-and-write-locks)).
    - Saved by each checkpoint to the statistics tree, with the last `commit_ts` they include ([TS-11](transactions-and-recovery.md#ts-11-checkpoint)), and loaded at open. An index's key there is `I`, graph, index (8 bytes big-endian each), distinct flag (1 byte: 0 entries, 1 distinct keys) (`src/catalog/stats.rs:26-32`).
    - **After a crash.** If recovery applied a commit above that `commit_ts`, open recounts every statistic exactly, by one scan of each node tree, adjacency tree and ONLINE index, before it returns ([TS-13](transactions-and-recovery.md#ts-13-recovery) step 7; `index::recount`, `src/index/mod.rs:998-1019`). No transaction runs during the recount, so it needs no snapshot (`src/catalog/mod.rs:750-754`).
- **Satisfies**: FR-CAT-001, FR-CAT-002, FR-CAT-003, FR-CAT-004, FR-CAT-005, FR-DB-001, FR-DB-005, FR-AUTH-002, FR-GQL-004, FR-PROC-004.
- **Evidence**:
  - Token maps: Neo4j (R-NEO `community/token-api/.../TokenHolder.java`) and Memgraph (R-MG `src/storage/v2/name_id_mapper.hpp`).
  - Token creation. Neo4j creates a missing token in a `synchronized` method that looks the name up again first (R-NEO `community/token-api/.../CreatingTokenHolder.java:62-71`), through an "inner transaction" (`TokenCreator.java:34`).
  - Token check. Neo4j resolves a token identifier only through its token holder, which throws for an unknown one (R-NEO `community/token-api/.../TokenHolder.java:77`).
  - Catalog names. PostgreSQL keeps catalog names unique with unique indexes, for example on `(relname, relnamespace)` (R-PG @ `1f22453` `src/include/catalog/pg_class.h:163`; `pg_namespace.h:60`). An insert that meets an uncommitted duplicate waits for its transaction to end (`src/backend/access/nbtree/nbtinsert.c:584-599, 220-235`), then fails if it committed (`nbtinsert.c:669`).
  - Parents. PostgreSQL's referential check in a transaction-snapshot transaction reads the latest committed rows and errors out on one its snapshot does not see (R-PG @ `1f22453` `src/backend/utils/adt/ri_triggers.c:2683-2699`). Removing either the parent lock or the children read fails test `a_schema_dropped_while_a_graph_is_created_in_it_leaves_no_orphan` (FINDING 187 on rmp task #31).
  - Graph types in use. PostgreSQL refuses to drop an object that others depend on unless the drop cascades (RESTRICT, SQLSTATE 2BP01, R-PG @ `1f22453` `src/backend/catalog/dependency.c:1160-1168`), and foreign-key creation locks the referenced table (`src/backend/commands/tablecmds.c:10188-10190`) (DECISION 196 on rmp task #31). Neo4j and Memgraph have no graph types.
  - Default names. Neo4j's default database is `neo4j` (`initial.dbms.default_database`, Neo4j Operations Manual, "Configuration settings"), and Memgraph creates a default database named `memgraph` (Memgraph documentation, "Multi-tenancy"), each named after the product. PostgreSQL's standard schema is `public` (R-PG @ `1f22453` `src/include/catalog/pg_namespace.dat:26-27`). GQL fixes no name (DECISION 191 on rmp task #31).
  - Bootstrap catalog. PostgreSQL `initdb` runs the server in bootstrap mode (`--boot`, R-PG @ `1f22453` `src/bin/initdb/initdb.c:1550, 1614`), which writes the initial catalog directly. Neo4j instead creates its initial database entries in a normal transaction at each start, when they are missing (R-NEO `community/kernel/.../dbms/database/SystemGraphInitializer.java:25-28`; `AbstractSystemGraphComponent.java:81-92` initialises only when it detects `UNINITIALIZED`; `community/neo4j/.../dbms/database/DefaultSystemGraphComponent.java:114-120`).
  - No authentication at bootstrap. In bootstrap and standalone mode PostgreSQL sets a fixed superuser identity and performs no client authentication; only the multi-user case calls `PerformAuthentication` (R-PG @ `1f22453` `src/backend/utils/init/postinit.c:907-922, 944-949`). `initdb` runs only those modes (`initdb.c:227, 1614, 3122`).
  - Owner at creation. PostgreSQL `initdb` takes the bootstrap superuser's name (`-U`, R-PG @ `1f22453` `src/bin/initdb/initdb.c:3302-3303`) and writes it into the bootstrap catalog (`initdb.c:1588-1589`), where that role owns the initial objects (`src/include/catalog/pg_authid.dat:18-25`). `initdb` defaults the name to the operating-system user (`initdb.c:3483-3485`); `create` has no such source, so the argument is required.
  - Count statistics: Neo4j keeps per-label counts and uses histograms only in tests; Kuzu uses default selectivities (M-QE §Q3.1).
  - Label changes. Neo4j updates the relationship counts of an added or removed label from the node's degrees per type and direction before the transaction, and the transaction's own relationship changes compensate (R-NEO `community/storage-engine-util/.../TransactionCountingStateVisitor.java:126-143`).
  - Below zero. Neo4j's consistency checker reports a count that differs from the one it computes (R-NEO `community/record-storage-engine/.../consistency/checker/CountsState.java:217-229`).
  - Recount. Neo4j's counts store is a tree written at checkpoint; when it cannot be trusted, start-up rebuilds it by a full count before transactions run (R-NEO `community/storage-engine-util/.../GBPTreeCountsStore.java:46-50`; `GBPTreeGenericCountsStore.java:195-201, 252-267`).
  - The ISO grammar has no statement that creates a directory ([S45], verified under OQ-005); the opengql grammar agrees (R-GQL `GQL.g4:3496-3537`, from M-QE §Q1.2).
- **Rejected**:
  - A catalog file separate from the transactional trees: FR-CAT-004 requires DDL and data changes to be atomic together.
  - Durable counters updated by every commit: one page image per commit on a hot page ([TS-09](transactions-and-recovery.md#ts-09-wal-and-group-commit)).
  - Stamped token entries created in the user's transaction: two transactions could commit the same name with two identifiers.
  - `create` recording no owner, passed to authorisation as absent; or a reserved principal name such as `system` (user decision 2026-10-07).
  - The first open committing the default schema and default graph (Neo4j): the owner would have to be kept outside the catalog until then, and every open would check for the objects. Writing them at create, before `CONTROL`, is atomic with the creation of the database.
  - A recount in the background after open: it would need a snapshot held for the whole count, whose old versions can make writers fail ([TS-18](#ts-18-indexes-and-constraints) rejects the same for index builds), or a protocol for concurrent changes that no reference shows.
  - Estimates rebuilt by sampling (the earlier rule): a sampler adds code, while one ordered scan per tree gives exact counts (NFR-SIMP-001).
  - A debug assertion on a count below zero: it panics under the commit latch in debug builds, while release builds hide the drift (FINDING 187 on rmp task #31).
  - Dropping a graph type in use by cascade: no requirement needs it. Dropping it unchecked: graphs would name a missing type (DECISION 196 on rmp task #31).
  - Naming the default schema and graph both `default` (no reference uses it) or both `lpg` (user decision 2026-10-08, DECISION 191 on rmp task #31).

## TS-18 Indexes and constraints

- **Decision**:
  - **Indexes.** Each index is a B+tree of its own, of stamped entries with compressed leaves ([TS-06](storage.md#ts-06-graph-layout)) and empty values. Keys use the order-preserving encodings of [TS-21](values-and-types.md#ts-21-values-and-types); identifiers are 8 bytes big-endian, the SRID 4 (`index_keys`, `src/index/mod.rs:443-476`):

    | Kind | Key |
    |---|---|
    | label or edge-type lookup | `(token, element_id)`, one entry per label of a node |
    | single-property, range | `(index_id, value, element_id)` |
    | composite | `(index_id, value_1, …, value_n, element_id)` |
    | point | `(index_id, SRID, Hilbert key, element_id)` of the canonical point (`spatial::canonical`), per CRS (2D or 3D), with exact distance as a post-filter |

    - A range or composite index covers an element that has its label or edge type and every indexed property present and not null; a point index, one that has its label or edge type and whose property is a point.
    - A reader uses an index only from the snapshot that sees its definition ONLINE (`online_index`, `src/index/mod.rs:1157-1166`), overlays its own record changes, and records each index or Hilbert range it reads as a read interval (`Transaction::scan_range`, `src/tx/mod.rs:515-522`; [TS-15](transactions-and-recovery.md#ts-15-serializable-isolation-and-write-locks)).
    - The label or edge-type lookup tree exists only when that index has been created (FR-IDX-001).
  - **Hilbert keys** (point index). 60 bits: 30 per axis in 2D, 20 per axis in 3D. The extents are fixed per CRS: for WGS-84 (SRIDs 4326 and 4979), longitude −180 to 180 and latitude −90 to 90; every other axis (Cartesian x, y and z, WGS-84 height) −1 000 000 to 1 000 000. A coordinate outside its extent is clamped to the edge; the exact-distance post-filter keeps results correct. There is no setting (NFR-SIMP-001).
  - **Side tree.** An unstamped, logged B+tree per POPULATING index. Key: the commit's `commit_ts` (8 bytes) and a sequence number within the commit (4 bytes), big-endian. Value: the operation (0 delete, 1 insert), then the index key (`src/index/side.rs:36-75`).
  - **Online build** (giant-graph path; `src/index/build.rs:1-45`):
    1. **Definition.** A transaction commits the definition POPULATING at timestamp `S`, with the index tree and the side tree, both created empty by that commit (`Engine::create_index`, `src/index/build.rs:589-626`). The create call then starts the build on thread `lpg-index-build` ([TS-02](architecture.md#ts-02-async-api-and-threading)).
    2. **Committers.** No index change is held in a write set. Under the commit latch, after validation and before the write-key set is registered ([TS-16](transactions-and-recovery.md#ts-16-commit-protocol) step 5), the committer derives the index changes from each record its write set changes and that record's latest committed version, for every index of the catalog cache on a graph it wrote (`derive`, `src/index/mod.rs:683-834`). The cache holds the latest committed definitions; every catalog commit updates it when it is applied. The write-write rule ([TS-15](transactions-and-recovery.md#ts-15-serializable-isolation-and-write-locks)) makes the versions the commit replaces the latest committed ones.
       - For an ONLINE index the changes are stamped puts and deletes of this commit, with their write keys. The memory of these changes, of their write keys and of the before-images of entries put again over a delete-stamped entry is reserved under the commit latch ([TS-14](transactions-and-recovery.md#ts-14-mvcc) Exception).
       - For a POPULATING index they are side-tree records.
       - A derived key longer than 1 024 bytes fails the commit with `InvalidArgument` ([TS-05](storage.md#ts-05-files-and-pages) Key size).
    3. **Scan.** The builder scans the latest committed elements of the graph without a snapshot and without the commit latch: it reads committed pages under their page latches and skips delete-stamped entries. Its tree read operations register for page reuse only ([TS-05](storage.md#ts-05-files-and-pages) Reuse), so it holds no old version. The scan can see a commit's batch half applied. An undone batch ([TS-16](transactions-and-recovery.md#ts-16-commit-protocol) step 6) raises the WAL's undo counter, `undo_epoch`, before it releases the latch; the builder reads the counter before the scan and compares it under the latch at the install of step 4. If it changed, the scan may hold an entry of the undone batch, which no side-tree record removes, so the build scans again (`scan_and_install`, `src/index/build.rs:368-447`).
    4. **Build and install.** It sorts the keys with an external merge sort into temporary files through the storage trait, and builds the index bottom-up, filled to 90 %, into pages taken in logged runs and owned by the build's record ([TS-05](storage.md#ts-05-files-and-pages) Build pages). It writes those pages with no latch held. One page-level commit installs the built tree into the index tree's existing root page (`install_into`, `src/storage/btree/write.rs:657-680`; [TS-05](storage.md#ts-05-files-and-pages): a root never moves), only if, under the commit latch, the cache still holds the index POPULATING and the undo counter is unchanged; otherwise the build's pages are released. The built entries carry no stamps (frozen, [TS-06](storage.md#ts-06-graph-layout)).
    5. **Replay.** It applies the side tree to the index in commit order, in chunks of 128 records. Each chunk is one page-level commit of frozen writes, made under the commit latch only while the cache holds the index POPULATING and the undo counter equals the value read before the chunk; otherwise nothing is written, and the chunk is read again (undo) or the build stops (drop) (`commit_chunk`, `src/index/build.rs:460-501`). The replay is idempotent: an insert of a present key and a delete of an absent key do nothing; an insert adds a frozen entry and a delete removes the entry. For every key with a record, the result is the operation of its last record, whatever the scan saw of it.
    6. **ONLINE commit.** A normal transaction marks the index ONLINE and drops the side tree. Its commit replays, under the commit latch, the side-tree records after the last one the builder replayed, and adds the entry and distinct-key counts the builder counted after its replay to the statistics, in one batch (`switch`, `src/index/mod.rs:949-973`; [TS-17](#ts-17-catalog-and-statistics)). No commit can fall between the last applied change and the state change. Readers use the index only from that snapshot on, which is above every change the build applied, so frozen entries and removed entries are correct for every reader of the index.
    7. **Open.** Open first releases the pages of every build record a crash left, then starts a build for every POPULATING index (`src/storage/engine.rs:751-764`). A build whose index tree is still one empty leaf starts at step 3. A build whose tree is installed resumes at step 5 and replays the whole side tree, which is idempotent, so the installed tree is never freed in one latched commit (`src/index/build.rs:289-302`). The side tree is logged, so it still holds every change since `S`.

    - **Waits.** Commits wait for a build only during its run, install, chunk, release and ONLINE commits, none of whose work depends on the index's size. No snapshot is held, so old versions do not accumulate (FR-IDX-005, FR-LIM-005). Sort memory is charged to the cap.
    - **Stop.** Close stops every build and leaves its index POPULATING (step 7). A build whose index or graph is dropped stops without writing to any tree, since every write checks under the latch that the cache holds the index POPULATING; its pages are released. Garbage collection does not free a dropped tree that a build reads, the element, index or side tree (`Builds::uses`, `src/index/build.rs:151-154`; [TS-14](transactions-and-recovery.md#ts-14-mvcc)).
    - **Backup.** A build runs during a backup; its install commit, the commit that installs a constraint's owned index, and each step of a release wait for the backup to end ([TS-26](operations.md#ts-26-backup-restore-import-and-export) Exclusion). The restored database holds the indexes and constraints as of the backup's `stop`: an index still POPULATING has its build restarted at open (step 7), after its build record, if any, is released; a constraint whose commit waited for the backup is absent.
    - **No FAILED state.** A build that fails, for example on a key longer than 1 024 bytes, leaves its index POPULATING; the next open builds it again (FINDING 214 on rmp task #33).
    - **Known liveness limit.** Each undo during a scan restarts that scan, without bound. Undos come only from ENOSPC or `MemoryLimit` during a commit; correctness holds, and close stops the build (DECISION 231 on rmp task #33).
  - **Constraints.**
    - Uniqueness and node key own a range index over their properties (`link`), created ONLINE and installed by the commit of the creating transaction (`Transaction::commit_installing`, `src/tx/mod.rs:765-786`). Uniqueness is checked in three places:
      - at creation, while the sorted keys stream into the bulk build: two adjacent keys with one value fail it (`UniqueSorted`, `src/index/build.rs:503-575`, a port of PostgreSQL's `enforceUnique`);
      - at write time: the writer takes the X lock on `(constraint, value)` ([TS-15](transactions-and-recovery.md#ts-15-serializable-isolation-and-write-locks)) and fails at once if the owned index's latest committed state holds the value for another element that the transaction has not written (`Transaction::unique_values`, `src/index/mod.rs:1284-1363`);
      - at commit, under the commit latch: no two added keys with one value, and no live entry with the value that the commit does not remove (`unique_violation`, `src/index/mod.rs:660-681`, a port of Turso's `check_index_for_conflicts`).
    - Property existence, property type and node-key existence are checked over the write set at commit (`check_constraint`, `src/index/mod.rs:634-658`).
    - **Missing properties.** An element that lacks a property of a uniqueness or property type constraint, or whose property is null, is not subject to it; property existence and node key require the property (FR-IDX-002).
    - **Property types.** The types of FR-IDX-002: a closed union of types `T` and of `LIST<T NOT NULL>` (`PropertyType`, `TypeSet`, `src/index/mod.rs:97-201`). `DURATION` covers both duration kinds; an empty list has every list type.
    - **Equal numbers.** `1` and `1.0` are one value under uniqueness, because their key encodings are equal ([TS-21](values-and-types.md#ts-21-values-and-types)). Whether Neo4j treats them so is not confirmed in the official documentation (PROGRESS 228 on rmp task #34).
    - A violation fails with the error kind `ConstraintViolation` (`src/storage/error.rs:101-104`). At write time it fails the statement, not the transaction. Its GQLSTATUS code is not assigned yet.
    - **Creation** takes the exclusive schema lock on its label or edge type in its graph. It validates the latest committed data, which is stable because writers of that label or type wait. It builds its owned index by steps 3 and 4 only: no writer of the label or type runs, so there is no side tree. Its pages are written without the commit latch, so writers of other labels and types do not wait (FR-IDX-006). It fails without creating the constraint if any element violates it.
    - **Drop.** Dropping a constraint drops its owned index; an owned index cannot be dropped alone. A graph drop drops its indexes and constraints ([TS-17](#ts-17-catalog-and-statistics) Dropping a graph; `drop_schema`, `src/index/mod.rs:1365-1406`).
  - Every index and constraint is defined on one graph.
- **Satisfies**: FR-IDX-001, FR-IDX-002, FR-IDX-003, FR-IDX-004, FR-IDX-005, FR-IDX-006, FR-TYPE-005, FR-API-004, FR-OPS-001, NFR-PERF-005.
- **Evidence**:
  - Neo4j point index: Hilbert-curve keys in its B+tree (R-NEO `community/spatial-index/.../curves/HilbertSpaceFillingCurve2D.java`, `HilbertSpaceFillingCurve3D.java`; `PointIndexReader`). Memgraph uses an in-memory R-tree (R-MG `src/storage/v2/indices/point_index_expensive_header.hpp:18`).
  - Hilbert keys. Neo4j uses 60 bits, "divisible by both 2 and 3", with `NBR_OF_BITS / dimensions` levels per axis (R-NEO `community/kernel/.../index/schema/config/SpaceFillingCurveSettings.java:53-60, 69`); its default extents are longitude ±180, latitude ±90 and ±1 000 000 on every other axis (`EnvelopeSettings.java:30-35, 61-80`); a point outside the extents "will be mapped as if on the edges" (`SpaceFillingCurveSettings.java:43-48`) by clamping (`community/spatial-index/.../curves/SpaceFillingCurve.java:328-334`).
  - Neo4j index population queues concurrent updates and flushes them into the populated index (R-NEO `kernel/.../api/index/MultipleIndexPopulator.java:92-118`). It applies the remaining queued updates inside the flip to ONLINE, under the populator lock (`MultipleIndexPopulator.java:708-712`). At start-up it repopulates every index found in state POPULATING (`kernel/.../api/index/IndexingService.java:328-342`).
  - PostgreSQL builds B-trees bottom-up from sorted input (R-PG `src/backend/access/nbtree/nbtsort.c:4`) and sorts larger-than-memory input by external k-way merge (R-PG `src/backend/utils/sort/tuplesort.c:11-15`).
  - Memgraph index entries carry timestamps and are pruned by garbage collection (R-MG `src/storage/v2/inmemory/label_property_index.hpp:62`).

- **Rejected**:
  - Building by inserting entries one at a time into the live tree: random I/O over the whole index at 1–10 % cache (NFR-PERF-005).
  - An R-tree: a second tree type with its own WAL and recovery code.
  - Index entries rechecked against records on every hit (Memgraph): one record read per hit.
  - An in-memory population queue (Neo4j): its size is bounded only by write traffic during a long build.
  - Scanning a pinned snapshot: under FR-LIM-005, old versions held for a long build would make concurrent writers fail instead of proceeding (FR-IDX-005).
  - Marking the index ONLINE after the replay, outside the commit latch: a commit between the end of the replay and the ONLINE commit would reach neither the index nor a replayed side tree.
  - Configurable Hilbert extents per CRS (Neo4j settings): no requirement needs them (NFR-SIMP-001).
  - Index entries in the write set: every write would read the catalog, and the commit would still have to reconcile them with definitions committed meanwhile (DECISION 215 on rmp task #33).
  - Installing the built tree under a new root page: the root would move, and a concurrent drop could free a page twice (DECISION 215).
  - A per-tree undo counter: more state for a rare ENOSPC event (DECISION 226).
  - Freeing an installed tree when its build restarts: one latched commit of O(index size); emptying it in chunks leaves one empty leaf per parent, so the free stays O(index size) (DECISION 226).
  - A retry cap with a FAILED state: a state this design does not have, and no requirement asks for it (DECISION 231).
  - A single type per property type constraint: narrower than Neo4j's closed unions and typed lists (DECISION 224 on rmp task #34).
