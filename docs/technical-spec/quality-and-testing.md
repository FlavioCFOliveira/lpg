# Quality and testing

## TS-29 Rust toolchain

- **Decision**: Rust edition 2024 with `std`. The minimum supported Rust version is 1.89, declared in `Cargo.toml`. It is raised only in a minor release, with a release note.
- **Satisfies**: NFR-PLAT-001, NFR-PLAT-002, NFR-REL-006.
- **Evidence**:
  - Edition 2024 needs Rust 1.85 or later ("The 2024 Edition is now stable", Rust 1.85.0 release notes, D-RUST).
  - `File::try_lock` ([TS-27](storage.md#ts-27-single-process-lock)) was stabilised in 1.89.0 (D-RUST).
  - `nalgebra` 0.35.0 declares `rust-version` 1.89.0 on crates.io.
  - The latest stable release is 1.98.1, of 2026-09-03 (D-RUST).
- **Rejected**: following the latest stable release, which would raise the minimum version with every Rust release.

## TS-30 Testing and conformance

- **Decision**:
  - **Parser.**
    - An oracle generated with antlr4rust from the unmodified `GQL.g4` of opengql/grammar, the trusted syntax reference ([TS-19](query-engine.md#ts-19-parser)), lives in a test-only crate that `lpg` does not depend on.
    - lpg's parser must accept and reject the same inputs as the oracle. Inputs:
      - the grammar's samples;
      - every GQL text in lpg's tests and in the conformance scenarios;
      - sentences generated from `GQL.g4` by a generator written in lpg.
    - A difference is a defect in lpg's parser, unless it is a type or function combination that the binder rejects on purpose ([TS-20](query-engine.md#ts-20-binder-planner-and-execution)).
  - **Semantics.** Scenarios from opengql/tck, and those openCypher TCK scenarios that apply to GQL, run through a small Gherkin-style runner written in lpg. lpg's own scenarios cover the rest. Every scenario names its clause or its feature identifier from the ISO features insert [S45]. Expected GQLSTATUS codes come from the ISO conditions insert, or from Neo4j where it has none ([interfaces.md](interfaces.md#public-api-shape)). The licences and attribution of the test artefacts are kept unchanged.
    - **Selection rule** (provisional, OQ-005). A scenario instance (a `Scenario`, or one `Examples` row of a `Scenario Outline`) runs when:
      1. every GQL text it runs is accepted by the parser generated from `GQL.g4`: the docstrings of the steps "executing query", "having executed", "executing control query", "executing the program" and "having executed the program", `Background` steps included, and the setup script of a named graph it uses;
      2. no construct of those texts needs a feature code outside the supported set ([TS-19](query-engine.md#ts-19-parser) Feature classification); and
      3. every feature tag it carries or inherits is supported, and it has no `@ignore` or `@Todo` tag and no capability tag lpg does not meet (`@MinNodeTypeKeyLabelsZero`, `@MaxNodeTypeKeyLabelsGTOne`; [TS-21](values-and-types.md#ts-21-values-and-types) IL003).
    - **gql-compat** (user decision 2026-10-08, "Como input, traduzido", rmp task #37): its mandatory and condition cases whose `features` are supported and whose texts pass rules 1 and 2 feed lpg's own scenarios, translated, with attribution (Apache-2.0).
    - **Runner** (rmp #52, `src/tck/`). The feature scanner is adapted from cyrs @ `6a6bb34` (MIT OR Apache-2.0). The artefact files that hold a selected scenario are vendored unmodified under `tests/tck/` with their `LICENSE` and `NOTICE`; `tests/tck/selection.tsv` records each instance's state under the rule above. Each scenario gets a new database and runs through `Session`; every statement runs under PROFILE, so the operator concurrency counter of NFR-PERF-007 is read for each. Result tables are compared in order or as multisets; temporal values are written as strings, as the openCypher TCK does; side effects are the statement's `Summary` counters; openCypher error details map to the codes of [interfaces.md](interfaces.md#gqlstatus-codes). A selected scenario that does something other than it expects is listed with its reason (a gate whose code has no `GQL.g4` construct, an expectation outside GQL, or a divergence the user decided to keep, which never counts as passed), and the runner checks that it does exactly that, including the cause's code where one is listed. An expected error may name a cause (`42000 caused by 22N27`), and the runner checks it. Every scenario names a feature code or a `GQL.g4` subclause. Every scenario text is a corpus of the parser differential.

  - **Durability.**
    - **Fault-injecting storage** (`src/storage/fault.rs`). It keeps in memory the unsynced writes, and the namespace changes not yet covered by a `sync_dir`. On a simulated crash it drops the unsynced writes, keeps a seeded subset of them, or tears them at 512-byte sectors; unsynced namespace changes are always lost.
    - **Faults** (R2, R9). EIO on the *n*-th call of `read_at`, `write_at`, `sync_data`, `create`, `rename`, `remove` and `sync_dir`. ENOSPC from a space budget. A misdirected write, which puts a page at another page's offset. A lost write, which drops a synced write.
    - **Failed `sync_data`** (R8). The file's unsynced writes stop being pending: a later `sync_data` succeeds without making them durable, and a crash loses them. This is the write-back failure PostgreSQL documents, where the data may be "entirely forgotten" and a retry "may be reported as successful" (R-PG `doc/src/sgml/config.sgml:12258-12264`).
    - **Crash-point sweep** (R1). A small fixed workload (commits, one checkpoint, one segment creation) is crashed after the *k*-th call of `write_at`, `sync_data`, `rename` and `sync_dir`, for every *k*, in every crash mode.
    - **Nth-failure sweep** (R2). The same workload fails the *n*-th call of each kind, for every *n*, with EIO and with ENOSPC.
    - **Oracle of both sweeps.** ENOSPC fails only the commit that needed the space, and the database stays usable. Any other failure sets the unusable latch. After a reopen, the state equals the state after a prefix of the commits that includes every acknowledged commit, and the integrity check ([TS-12](storage.md#ts-12-checksums-corruption-and-integrity-check)) passes.
    - **Valid page images.** The tests of build pages and of backups taken during an index build or a constraint creation also check that every page below `page_count` holds a valid image, in the data file or in a dirty frame of the pool, as migration needs ([TS-28](operations.md#ts-28-format-versioning-and-migration)); the integrity check does not read a build record's pages ([TS-12](storage.md#ts-12-checksums-corruption-and-integrity-check)) (`assert_every_page_valid`, `src/storage/btree/bulk/tests.rs:483-492`, `src/index/tests.rs:2088-2097`).
    - **Checkpoint order** (R3). The call log pins the order of [TS-11](transactions-and-recovery.md#ts-11-checkpoint): data `sync_data`, then the `CONTROL` write and its `sync_data`, then each recycling `rename` or `remove` with its `sync_dir`.
    - **Seeds** (R5). Every seeded fault test draws a random seed unless the environment variable `LPG_SEED` is set, and prints the seed when it fails.
    - **Pause and fail points** (R10). Test-only points (`cfg(test)`) between the apply and the join of a commit, inside the checkpoint's revisit loop, and inside segment creation make interleavings deterministic. They replace sleeps and polling. A test installs a hook that runs at a named point.
      - In the code: `segment_created`, after a segment is created and its name is durable, and `before_close`, in the WAL writer after its health check and before it takes the commit latch to close a group (`TestPoints`, `src/storage/wal.rs:809-843`; run at `wal.rs:1061` and `wal.rs:1197`). Their first user is `audit_a_failed_capture_never_reaches_the_wal` (`src/tx/commit/tests.rs:709`).
      - `bulk_page`, in a bulk build after each page it writes, with no latch held (`src/storage/btree/bulk.rs:333`), and `batch_body`, in every logged write batch after its body has changed its pages and before its images are captured, with the commit latch held: a reader without the latch sees the batch half done there, and an error its hook returns makes the batch undo itself (`src/storage/btree/write.rs:443`).
      - The index build's phases ([TS-18](catalog-and-indexes.md#ts-18-indexes-and-constraints)): `Scanning`, `Scanned`, `Installed`, `ChunkRead`, `Replaying`, `BeforeOnline`, and `Validating` in a constraint creation (`Phase`, `src/index/build.rs:84-106`), a `cfg(test)` hook.
      - Fail point `gc::FAIL_SEED` (`src/tx/gc.rs:251-256`): the seed scan of [TS-14](transactions-and-recovery.md#ts-14-mvcc) fails with `MemoryLimit` for the listed locations. It uses a `std` `Mutex` and is compiled out under `loom` and `shuttle`.
      - Fail point `Mvcc::gc_fail_read` (`src/tx/mvcc.rs:98-103`, read at `src/tx/gc.rs:170-177`): the next garbage-collection pass that takes work from its queues fails with `MemoryLimit` before its first read, as `Pool::fetch` does when every frame is pinned or dirty. Test `a_pass_that_fails_after_taking_its_work_puts_it_back` (`src/tx/tests/gc.rs:632`) checks that the work is put back (audit F3 on rmp #35).
      - `after_apply`, between the apply and the join of a commit (`src/tx/commit.rs:251`), and `checkpoint_revisit`, inside the checkpoint's revisit loop (`src/storage/checkpoint.rs:210`); both are declared in `src/storage/wal.rs:826-828`.
      - `backup_started`, in a backup after step 1, and `backup_copied`, after the data file is copied and before `stop` is read (`src/storage/wal.rs:829-833`).
    - **Transaction workload** (`Workload::Transactions`, `src/suites/fault.rs`). Both sweeps and the page-copy failure sweep also run 12 transactions, every third under snapshot isolation and the others serializable. Each has puts and a delete stamp, and updates property `P` of a node and of an edge of the default graph; the fourth drops a tree; the eighth creates a graph with 40 nodes and 39 edges, which the eleventh drops; the tenth deletes a node with its edge. After the second, the workload creates a range index on nodes and one on edges and waits for each online build. A checkpoint follows the ninth, and a garbage-collection pass is made durable after every sixth. ENOSPC of a reservation and a refused memory reservation fail only that transaction, build or pass. After the reopen, with index builds held until then, no entry is stamped above the recovered `commit_ts` (`assert_no_stamp_above`, `src/suites/mod.rs`); what snapshots see, graph properties included, equals the model after a prefix of the transactions with every returned one; the restarted builds end ONLINE, an index creation that returned is kept, and the integrity check, with the cross-tree and index checks and the reconciliation of the catalog tree with the catalog cache and the directory, passes; once the seed scan has run, a pass with no snapshot open leaves no entry with a delete stamp at or below its horizon (`assert_stamps_collected`).
    - **Process crash.** A child process is killed with `kill -9` during a write workload on ext4 and on XFS. On the reference machine the tests use the ext4 filesystem and an XFS directory that the user mounts and provides; the tests run without privileges.
      - A transaction thread (`src/suites/kill.rs:25-46`) runs transactions, alternately serializable and snapshot isolation, that leave delete stamps and create nodes and edges with property `P`, and creates, fills and drops a graph at its first commit and every 16th after it. An index thread builds range indexes on those nodes and edges in turn and drops the one it built before, so one index stays ONLINE and maintained. After the reopen, with index builds held until then, no entry is stamped above the recovered `commit_ts`; the interrupted builds then end ONLINE before the checks. The index thread prints each index whose build returned and each index whose drop committed; after the builds end, each index the parent kept ONLINE at the last close and the last index whose build returned in the child are present and ONLINE, and each index whose drop was printed is absent (audit F1 on rmp #35). After the reopen, every printed drop is dropped and, once the seed scan and a pass have freed the dropped trees, no entry keeps a delete stamp at or below the pass's horizon and the integrity check passes. A full run fails unless at least one drop was printed and at least one checkpoint recycled or removed a segment; the first child of a full run fills the WAL past its first segment and checkpoints before its workload, so a checkpoint recycles whatever the file system's speed.
    - **File system of each run.** Both suites print, for each directory, the file-system type and source of its mount as `findmnt --target` reports them, and a lab directory whose type differs from its variable's (ext4 for `LPG_LAB_EXT4`, XFS for `LPG_LAB_XFS`) fails the run (`suite_dirs`, `src/suites/mod.rs`). The directories run at once, each on its own thread (`each_dir`, `src/suites/mod.rs`).
    - **What the ext4 and XFS runs show.** File-system compatibility and consistency after a process crash. `kill -9` leaves the page cache to the kernel, which writes it back, and the fault-injecting storage skips the device flush, so neither suite observes a missing `fsync`: with the WAL's `sync_data` removed, the kill suite still passed (audit mutation M6, FINDING 245 on rmp #35). Durability across a power loss on ext4 and XFS is [unverified point 19](#unverified-points).
  - **Regression tests.** A test added for a defect must fail when the defect's fix is reverted (mutation) in the default test build, where debug assertions are on (Speed, below). Audit finding m-c: `audit_a_failed_capture_never_reaches_the_wal` detected its defect only in release builds, because in debug a debug assertion in the WAL writer failed first; it now fails under the mutation in debug and in release (TEST 83 and 84 on rmp task #15).
  - **Concurrency.**
    - **`crate::sync` facade** (R11; `src/sync.rs`). The crate imports every synchronisation primitive (`Mutex`, `RwLock`, `Condvar`, atomics, `Arc`) from `crate::sync`, which re-exports `std::sync`, or `loom::sync` under `cfg(loom)`, or `shuttle::sync` under `cfg(shuttle)`.
      - `Arc`, `PoisonError` and `TryLockError` come from `std` under every `cfg`: `loom`'s `Arc` cannot be coerced to `Arc<dyn Trait>`, and `shuttle` re-exports `std`'s `Arc`.
      - The module's shape follows Turso's `core/sync.rs` (R-TURSO @ `8cc059b`, MIT); its attribution and licence notice are kept in `src/sync.rs`.
    - `loom` explores every interleaving of small models. Thirteen models: a cancel racing a commit on a transaction's status, with a second model that must fail when the commit ignores the status (`src/api/status.rs`; rmp #49); the memory accountant; the lock table (queue order, and deadlock cycles of two and three transactions and through a waiting request); publish order; the snapshot registry against the garbage-collection horizon ([TS-14](transactions-and-recovery.md#ts-14-mvcc)), one model for the first block and one for an overflow block; two creators of one token ([TS-17](catalog-and-indexes.md#ts-17-catalog-and-statistics) Tokens; `src/catalog/tests.rs:797`); the index side-tree replay and ONLINE switch ([TS-18](catalog-and-indexes.md#ts-18-indexes-and-constraints); `loom_side_tree_replay_and_online_switch`, `src/index/tests.rs:2939`); a build's run of pages against an undone batch on the real data file ([TS-05](storage.md#ts-05-files-and-pages) Build pages; `loom_a_build_run_and_an_undone_batch_never_share_a_page`, `src/storage/btree/bulk/tests.rs:593`). Under `cfg(loom)` a registry block has one slot.
    - `shuttle` runs randomised schedules of larger tests: the memory accountant, and the commit latch, the WAL writer and the checkpointer under transaction commits and under batch commits ([TS-16](transactions-and-recovery.md#ts-16-commit-protocol) Batch), and graph writers with checkpoints, whose statistics must stay exact (`src/storage/graph/tests.rs:1185`) (D-SHUTTLE). Under `shuttle` the WAL writer skips its gather window ([TS-09](transactions-and-recovery.md#ts-09-wal-and-group-commit)): the window ends by timeout, and `shuttle`'s `Condvar::wait_timeout` never times out (`src/storage/wal.rs:598-603`).
    - **Stress profile** (R7). The concurrency tests also run as at least 16 concurrent copies, outside the default run, before a task closes.
  - **Isolation** (from Sprint 2, with [TS-14](transactions-and-recovery.md#ts-14-mvcc) and [TS-15](transactions-and-recovery.md#ts-15-serializable-isolation-and-write-locks); R12).
    - The Hermitage scenarios run against lpg's transaction API, on tree entries and on nodes of the default graph (`src/tx/tests/hermitage.rs`). lpg is serializable by default, so G2 and write skew must abort (P-TEST §7).
    - Elle checks list-append and rw-register histories recorded from lpg transactions, on tree entries and on graph operations: lists as list properties of nodes, registers as a property of edges, with the seven transaction templates of Turso's chaotic Elle workloads (R-TURSO @ `8cc059b` `testing/concurrent-simulator/chaotic_elle.rs`, MIT, copied with its notice into `src/tx/tests/elle.rs`). `elle-cli` 0.1.11, which bundles Elle 0.2.7, runs as an external tool, outside the crate (`src/test_support/history.rs`). Each process writes its histories to `/tmp/lpg-histories/<name>-<pid>.edn`, a tool intermediate on the RAM-backed `/tmp`, so the concurrent copies of the stress profile do not share a file; a passing test removes its file, a failing one keeps it (`src/test_support/history.rs:167-174, 192-226`). The JVM runs with `-XX:TieredStopAtLevel=1` (C1 compiler only): `elle-cli`'s JSON output was byte-identical to the default tiered compilation on 11 histories, and its CPU time fell from 4.7–4.9 s to 1.9–2.0 s per history (Speed, below). It is invoked with `--consistency-models` only: anomalies listed with `--anomalies` are added to the prohibited set.
  - **Memory** (R13). Planned, not built: a separate test binary that counts allocations with a global allocator over cycles of open, workload and close, and compares them with the memory accountant ([TS-08](storage.md#ts-08-buffer-pool-and-memory-cap)), to measure the gap of [unverified point 15](#unverified-points). No such binary exists (checked for rmp #35, 2026-10-08), so point 15 stays open. A global allocator needs `unsafe impl GlobalAlloc` (`pub unsafe trait GlobalAlloc`, <https://doc.rust-lang.org/std/alloc/trait.GlobalAlloc.html>); whether test code outside the crate root may use it under NFR-SAFE-001 is not decided.
    - **Heap of a test thread.** Tests that bound memory the accountant does not see measure the peak heap of their own thread with the dev-dependency `allocation-counter` (Crates, below), for example the cross-tree integrity check ([TS-12](storage.md#ts-12-checksums-corruption-and-integrity-check); `src/storage/graph/tests.rs:1106`).
  - **Speed.**
    - Tests run as fast as possible without losing effectiveness: a change that makes them faster is accepted only when measurement shows it removes no tested property (user requirement, DECISION 67 on rmp task #15).
    - **`NoFlush` storage** (`src/test_support/mod.rs:140-153`): the file system with `sync_data` and `sync_dir` as no-ops; every other call is unchanged. The engine, B+tree, free-list and pool tests, the commit test `audit_a_failed_capture_never_reaches_the_wal`, and the data-file and `CONTROL` unit tests use it. None of them crashes the operating system, so what they read back comes from the operating-system cache whether or not it was flushed; the flush proves nothing there. The tests of the file-system storage (`storage::fs`) and of the fault-injecting storage (`storage::fault`) keep real flushes. Crash tests use the fault-injecting storage, which models durability itself (DECISION 77 on rmp task #15).
    - **Hangs.** A wait on background work (the garbage collector) is bounded by `test_support::wait_until` (30 s) and fails its test with a message. A test that checks a thread is gone after `close` polls with it too: `pthread_join` can return before the thread's `/proc/self/task` entry is removed (`the_collector_thread_runs_while_the_database_is_open`, `src/tx/tests/gc.rs:430-450`; listed after close in 30 of 3 200 runs before the change, 0 of 3 200 after, PROGRESS 234 on rmp task #33). The default nextest profile kills a test after 10 periods of 60 s (`.config/nextest.toml`).
    - **Space in `/tmp/lpgram`.** The nextest test group `disk-heavy` (`.config/nextest.toml`) runs at most three tests at once from the modules that hold every test peaking at 60 MiB or more. It bounds the peak space of a default run in `/tmp/lpgram`, which shares the user's `/tmp` quota: 754 MiB with the cap, 1.9 GiB with 16, and a default run is no faster with 16 (2026-10-11). In a run with the lab directories it also bounds the lab space: the kill suite and two sweeps peaked at 4.7 GiB on the 8 GiB XFS lab file system, where the kill suite alone takes 3.5 GiB.
    - **Parallel crash suites.** The runs of one fault-injection sweep (one per crash point and crash mode, per failure and per page-copy failure) share nothing: each has its own directories and fault storage. They run on two threads per lab directory (`run_all`, `SWEEP_THREADS`, `src/suites/fault.rs`), with the same seeds and oracles; the sweep asserts that the runs that ended equal the runs planned, and the first failing run fails the test. The lab directories of both suites run at once. The iterations of the kill suite in one directory share its database and stay in order. Two threads per directory, not more: alone, the restore sweep on ext4 took 99.3 s on 1 thread, 33.6 s on 4 and 37.4 s on 16, with 100, 133 and 565 CPU seconds, most of them in the kernel; in a full run on ext4 and XFS, 2 threads took 145.4 s and 4 threads 163.8 s.
    - **Order.** The slowest tests start first (nextest `priority`, `.config/nextest.toml`): the kill suite and the million random operations, then the restore and commits sweeps.
    - Tests build at `opt-level = 1` (`[profile.test]`, `Cargo.toml:42-43`). The `test` profile inherits `dev` (D-CARGO), so debug assertions and overflow checks stay on; `cargo test --message-format=json` reports both on at `opt-level` 1 (2026-10-03). `opt-level` 2 was measured on 2026-10-11 and not adopted: a default run took 0.6 s less and each rebuild after an edit 0.8–1.3 s more.
    - **Linker.** The `x86_64-unknown-linux-gnu` target links with LLD by default since Rust 1.90 (D-RUST190); the test binary's `.comment` section names `Linker: LLD 23.1.1` (2026-10-11). No linker is configured.
    - **Gate runner** (`.config/gates.sh`). It runs at once, each in its own target directory under `/dev/shm/lpg-target`, the gates that do not depend on each other: `cargo fmt --check`, `clippy`, `clippy` under `--cfg fuzzing`, nextest (with the lab directories when `LPG_LAB_EXT4` and `LPG_LAB_XFS` are set), `loom` and `shuttle`. It then runs the stress profile alone, since its load is part of its design, and deletes the single-use target directories (`cfgfuzz`, `loom`, `shuttle`). `loom` and `shuttle` cannot share a build: each `--cfg` changes `RUSTFLAGS`, so every crate is rebuilt, and `src/sync.rs` selects one checker per build.
    - **Fuzzing recipe.** Long fuzz runs use libFuzzer's fork mode, one job per process, with timeouts and out-of-memory exits counted as failures: `cargo +nightly fuzz run --target-dir /dev/shm/lpg-target/<dir> <target> <corpus> -- -fork=<N> -ignore_timeouts=0 -ignore_ooms=0 -artifact_prefix=<dir>/`. Fork mode ignores timeouts and OOMs unless told otherwise (`ignore_timeouts` and `ignore_ooms` default to 1, `ignore_crashes` to 0) and stops at the first crash it does not ignore (D-FORK). `cargo fuzz coverage` builds in `fuzz/target/<triple>/coverage` unless `--target-dir` is given (D-CARGOFUZZ), so it is always given.
  - **Bolt.**
    - The server endpoint is tested with the official Neo4j drivers for Java, Python, JavaScript, .NET and Go, and with the crate's own client.
    - The client endpoint is tested against the crate's server and against a Neo4j server that supports Bolt 5.0 or later.
    - `neo4rs` is excluded.
  - **Licences.** `cargo-deny` checks licences on every build of the dependency set.
  - **Performance.** The NFR-PERF-002 baseline (LDBC SNB Interactive and BI, micro-workloads; against Neo4j and Memgraph) runs on the reference hardware. Giant-graph efficiency is measured with the cache at 1 % and 10 % of the data (NFR-PERF-005, NFR-PERF-006). The M-LAYOUT harness is the starting point for the micro-workloads.
    - Sprint 3 defines the micro-workloads, each as a GQL text with its expected result, and checks their results. Their timing, and [unverified point 8](#unverified-points), move to Sprint 6 (user decision 2026-10-08, "Definir agora, medir no S6", rmp task #39).

- **Evidence**:
  - SQLite simulates OS crashes and power failure in a test VFS (R-SQLITE `src/test6.c`).
  - turso has a deterministic simulator and a differential oracle (R-TURSO `testing/simulator`, `testing/differential-oracle`).
  - The fault model and test dimensions of Turso and libSQL compared with lpg's, and recommendations R1–R13: [P-TEST](../evidence/research/research-04-turso-libsql.md) §2–§6. On 2026-10-03 the user adopted R6 (`opt-level` 1), R7, R9, R11 and R12, which widen the scope; R1–R3, R5, R8, R10 and R13 fall within the existing scope of tasks #20 and #22. They are recorded in rmp task #20 comments 69 and 70, task #2 comment 71, task #23, DECISION 67 on task #15, and sprint 1 comment 28.
  - Nth-failure loop. SQLite's `faultsim` fails the *N*-th operation for *N* = 1, 2, … until no fault fires, then checks the result (R-LIBSQL `libsql-sqlite3/test/malloc_common.tcl:41-50, 326-385`).
